



# AI Agent 四层记忆架构设计

## 介绍

没有记忆的 Agent 只是一次性问答机器人；拥有四层记忆的 Agent 才具备长期交互和企业应用能力

四层记忆本质解决四个问题：

| 问题      | 解决方案           |
| ------- | -------------- |
| 刚才说了什么？ | Window Memory  |
| 以前聊过什么？ | Summary Memory |
| 长期喜欢什么？ | Long Memory    |
| 用户是谁？   | Profile Memory |

**记忆架构四层设计**

```
                 用户输入
                     │
                     ▼
          ConversationManager
                     │
      ┌──────────────┼────────────────┐
      ▼              ▼                ▼
 WindowMemory   SummaryMemory   LongTermMemory ，Profile Memory
      │              │                │
      └──────────────┼────────────────┘
                     ▼
             PromptBuilder
                     │
                     ▼
              create_agent()
                     │
                     ▼
                    LLM
                     │
                     ▼
             AI Response
                     │
                     ▼
          ConversationManager.save()
```

**和Checkpointer 的区别**

这是一个非常关键的问题。很多人在学习 LangChain 1.0 Agent 时，会把：

- **四层记忆架构（Memory Architecture）**
- **LangGraph/LangChain 1.0 Checkpointer**

混在一起。实际上它们解决的是**两个不同层面的问题**。

- Checkpointer 保存 Agent 的运行状态（State）
- 四层记忆保存 Agent 需要理解的用户信息（Memory）

## 架构总览

 AI Agent 实现了四层记忆架构，将记忆能力拆分为**记忆存储**与**记忆提取**两大子系统，分别负责数据的持久化管理和智能化处理。

```
┌──────────────────────────────────────────────────────────────────┐
│                       ConversationManager                        │
│                     (对话管理器 · 全局入口)                         │
│                                                                  │
│   save_user() → save_ai() → build_prompt() → MemoryManager      │
└──────────────┬────────────────────────────────────┬──────────────┘
               │                                    │
    ┌──────────▼──────────┐              ┌──────────▼──────────┐
    │   第一部分：记忆存储   │              │  第二部分：记忆提取   │
    │   (memory_save/)     │              │ (memory_retrieval/) │
    │                      │              │                     │
    │  WindowMemory    L1  │              │  SummaryAgent   L2  │
    │  SummaryMemory   L2  │              │  LongMemoryAgent L3 │
    │  LongMemory      L3  │              │  ProfileAgent   L4  │
    │  ProfileMemory   L4  │              │  MemoryManager      │
    │  PromptBuilder       │              │   (更新调度器)        │
    └──────────────────────┘              └─────────────────────┘
```

# 准备

##  向量数据库

   在企业级 AI Agent 中，**向量数据库（如 ChromaDB）并不是用来替代 MySQL、Redis，而是专门解决"语义记忆检索"的问题。**

如果没有向量数据库，Agent 就无法真正拥有"长期记忆"

**一、为什么需要向量数据库？**

假设用户第一次聊天：

```
我喜欢使用 LangChain 开发 AI Agent。
```

第二次聊天（一个月后）：

```
推荐一个适合我的 Agent 开发框架。
```

如果系统没有长期记忆，它只能看到当前问题：

```
推荐一个适合我的 Agent 开发框架。
```

它根本不知道：

```
用户喜欢 LangChain。
```

因此回答可能是：

```
AutoGen
CrewAI
LangGraph
Semantic Kernel
```

这些都可能推荐。

**二、ChromaDB 保存什么？**

ChromaDB 保存的是**自然语言记忆**。

例如：

```
用户喜欢 Python。

用户喜欢 LangChain。

用户正在开发医疗知识图谱。

用户计划学习多智能体。

用户曾开发电商数据分析系统。
```

这些都属于：

**长期知识（Long-term Memory）**

而不是数据库中的固定字段。



**为什么越来越多企业采用 Chroma？**

主要有三个原因：

| 优势              | 说明                            |
| --------------- | ----------------------------- |
| **语义检索**        | 根据含义而不是关键词搜索长期记忆。             |
| **支持长期个性化**     | 保存用户偏好、经历、技能、长期目标等信息。         |
| **降低 Token 成本** | 每次只检索最相关的几条记忆，而不是把所有历史都发送给模型。 |

**`query_texts` 的作用**

1. 查询文本

   - `query_texts` 是一个 **列表**，每个元素都是你想检索的查询语句
   - 在内部，ChromaDB 会：
     1. 将每个查询文本转换成向量（embedding）
     2. 与数据库中所有文档向量进行相似度计算
     3. 返回最相似的文档

2. 列表形式

   - 支持同时对多个文本查询：


3. 结合 `n_results`

   - `n_results=1`：每个查询文本只返回最相似的 **1条文档**
   - 如果 `n_results=3`，则返回最相似的 **前3条文档**

## redis 数据库

在企业级 AI Agent 中，**Redis 不是用来替代向量数据库，也不是用来替代关系数据库，而是负责"高速、实时、结构化"的记忆存储。**

如果没有 Redis，智能体虽然可以工作，但会出现：

- 对话连续性差
- 响应速度慢
- 数据库压力大
- 用户画像查询效率低

因此，Redis 已成为企业级 Agent Memory 的标准组件之一。

**Redis 的作用就是：**

**高速保存和读取当前会话的重要信息，让 Agent 拥有"短期记忆"**

**Redis 负责：**

- Window Memory（滑动窗口记忆）
- Profile Memory（用户画像）
- Session Cache（会话缓存）
- Token Cache（Token缓存）

### redis 序列化和反序列化

**一、为什么要序列化**

Redis 是一个 **键值数据库**，底层只认识 **字节数据（bytes）**。
当我们往 Redis 存入复杂的 Python 对象（如字典、列表、自定义类）时，
就必须把它 **序列化为字符串或二进制** 才能存进去。

> 简单说：
>
> - **序列化（serialize）**：把 Python 对象 → 转成可存入 Redis 的字节或字符串
> - **反序列化（deserialize）**：从 Redis 拿出来的字节 → 转回 Python 对象



**二、Redis 默认存储的类型**

当你执行：

```
r.set("user", {"name": "Tom", "age": 20})
```

你以为它存了一个字典，其实会报错，因为 Redis 不知道这个对象是什么。
它只支持像这样：

```
r.set("user", "Tom")  # 字符串
```

所以我们需要把字典“转成字符串”或“转成字节流”。

**三、JSON 序列化示例**

```python
import redis
import json

r = redis.StrictRedis(host='localhost', port=6379, db=0)

# Python 字典
user = {"name": "Tom", "age": 25, "tags": ["python", "ai"]}

# 序列化：dict → JSON 字符串
r.set("user:1", json.dumps(user,ensure_ascii=False))

# 从 Redis 取出（二进制 bytes）
data = r.get("user:1")

# 反序列化：JSON 字符串 → dict
user_obj = json.loads(data.decode())

print(user_obj)
# 输出: {'name': 'Tom', 'age': 25, 'tags': ['python', 'ai']}

```

- **ensure_ascii=True（默认值）**：将所有非 ASCII 字符转成 `\u` 开头的 Unicode 转义序列（比如中文“你好”变成 `\u4f60\u597d`）。
- **ensure_ascii=False**：保留原始字符，直接输出人类可读的形式（比如直接输出 `"你好"`）

## 1. L1 — 窗口记忆存储 (WindowMemory)

### 1.1 设计目标

模拟人类的**工作记忆**，保留最近若干轮对话作为即时上下文。

在企业级智能体中，**滑动窗口记忆（Sliding Window Memory）是最基础、也是最重要的一层短期记忆设计**。

​     滑动窗口记忆是企业 Agent 的“短期大脑”，它负责让模型只关注当前任务相关的信息，降低 Token 成本，提高响应速度，同时保证多轮对话连续性。

### 1.2 存储实现

基于 Redis List，实现固定大小的滑动窗口。

```python
import redis
from dotenv import load_dotenv
import os
import json
#读取配置我呢见
load_dotenv()
"""
窗口记忆，记录最近的4轮的窗口记忆
"""
class WindowMemory:

    def __init__(self,session_id:int):
        self.client = redis.StrictRedis(host="localhost",port=6379,db=0)
        #设置key
        self.key = f"chat_widow:{session_id}"
        #获取轮次
        self.window_size = int(os.getenv("WINDOW_SIZE"))
        # 获取过期时间
        self.window_time = int(os.getenv("WINDOW_TIME"))
    #添加记忆
    def add(self,role:str,content:str):
        #构建一个字典
        msg ={"role":role,"content":content}
        #序列化
        msg_json = json.dumps(msg,ensure_ascii=False)
        #列表完成数据追加
        self.client.rpush(self.key,msg_json)
        #设置窗口的限制条数，剩下的删除
        self.client.ltrim(self.key,-self.window_size,-1)
        #设置过期时间
        self.client.expire(self.key,self.window_time)
    #查询记忆
    def load(self):
        msg = self.client.lrange(self.key,0,-1)
        #数据进行反序列化
        return [ json.loads(x) for x in msg]

#测试函数
def test():
     w = WindowMemory(1)
     #模拟人类消息添加
     w.add("user","你好")
     #模拟AI回复消息
     w.add("ai","你好，我是AI助手")
     #模拟人类消息添加
     w.add("user","你好1")
     #模拟AI回复消息
     w.add("ai","你好1，我是AI助手1")
     #模拟人类消息添加
     w.add("user","你好2")
     #模拟AI回复消息
     w.add("ai","你好2，我是AI助手2")
     w.add("user","你好3")
     #模拟AI回复消息
     w.add("ai","你好3，我是AI助手2")
     #查询记忆
     rs = w.load()
     print(rs)
if __name__ =="__main__":
    test()




```

`redis.ltrim(self.key, -self.window_size, -1)` 是 Redis **列表(List)截取命令 LTRIM** 的 Python 调用方式。

它的作用：**保留 Redis List 中指定范围的数据，其它删除**

```
保留列表最后 5 条数据。其它删除
redis.ltrim("chat_history", -5, -1)
```

## 2. L2 — 摘要记忆存储 (SummaryMemory)

### 2.1 设计目标

摘要记忆（Summarization Memory）是**企业级 AI 智能体中最重要的记忆技术之一**。它的核心思想是：

> **将大量历史对话压缩成一段能够保留关键信息的摘要，在后续对话中作为上下文继续提供给大模型。**

企业几乎不会把所有聊天记录都发送给大模型，而是采用**滑动窗口 + 摘要记忆 + 长期记忆**的组合方式，其中摘要记忆承担了承上启下的作用。

**为什么企业一定要用摘要记忆？**

假设有一个 AI 客服。

用户已经连续聊了 300 轮。

如果每次请求都把这 300 轮全部发送给 LLM：

```
历史记录
↓

第1轮
第2轮
...
第300轮

↓

LLM
```

会出现很多问题：

- Token越来越大
- 成本越来越高
- 响应越来越慢
- 超过模型上下文长度

因此企业不会一直保留全部聊天，而是：

```
前100轮
        ↓
     自动总结
        ↓
    一段摘要（500字）
最近20轮
        ↓
摘要 + 最近聊天
        ↓
       LLM

```

这样上下文长度几乎固定。

### 2.2 存储实现

安装

```
pip install "psycopg[binary, pool]"
```

基于 PostgreSQL conversation_summary 表，使用 UPSERT 语义。

```python
from psycopg_pool import ConnectionPool

pool = ConnectionPool(
    conninfo="host=127.0.0.1 port=5432 dbname=postgres user=postgres password=1234",
    min_size=2, max_size=10
)

class SummaryMemory:
    def load(self, session_id):
        """读取指定会话的摘要"""
        with pool.connection() as conn:
            with conn.cursor() as cur:
                cur.execute(
                    "SELECT summary FROM conversation_summary WHERE session_id=%s",
                    (session_id,)
                )
                row = cur.fetchone()
                return row[0] if row else ""

    def save(self, session_id, summary):
        """写入或更新摘要 (UPSERT)"""
        with pool.connection() as conn:
            with conn.cursor() as cur:
                cur.execute(
                    """
                    INSERT INTO conversation_summary(session_id, summary)
                    VALUES(%s, %s)
                    ON CONFLICT(session_id)
                    DO UPDATE SET summary=EXCLUDED.summary, update_time=NOW()
                    """,
                    (session_id, summary)
                )
            conn.commit()
```

**关键sql 解释**

```sql
      INSERT INTO conversation_summary(session_id, summary)
                    VALUES(%s,%s)
                    
                    ON CONFLICT(session_id)
                    DO UPDATE SET
                        summary=EXCLUDED.summary,
                        update_tim	e=NOW()
```

这段 SQL 是 PostgreSQL 中非常常用的 **UPSERT（Insert Or Update）语法**，意思是：

**如果 session_id 不存在，就插入一条摘要记录；如果 session_id 已经存在，就更新原来的摘要**

在 AI Agent 的 Memory 场景中非常常见。

- ON CONFLICT(session_id) 如果发生冲突，冲突是session_id 已经存在，不要报错
- DO UPDATE 冲突以后执行更新，也就是：不要插入新的。改旧数据
- summary=EXCLUDED.summary：  EXCLUDED是 PostgreSQL 一个特殊对象。代表：本来准备 INSERT 进去的新数据

**连接池解释**

```
pool = ConnectionPool(
    conninfo="host=127.0.0.1 port=5432 dbname=postgres user=postgres password=1234",
    min_size=2,
    max_size=10
)

```

作用是：提前创建并维护一批 PostgreSQL 连接，需要时直接拿一个使用，用完归还，而不是每次重新创建连接

### 2.3 数据库表结构

```sql

    summary     TEXT NOT NULL,          -- 摘要内容
    create_time TIMESTAMP DEFAULT NOW(), -- 创建时间
    update_time TIMESTAMP DEFAULT NOW()  -- 更新时间
);
```

## 3. L3 — 长期记忆存储 (LongMemory)

### 3.1 设计目标

   长期记忆就是 AI 的"个人档案"，用于保存用户长期稳定、不经常变化的重要信息，使 AI 能够跨会话持续了解用户，从而提供更加个性化、连续性的服务。

**长期记忆（Long-term Memory）最核心的思想**

```
保存用户长期不会频繁变化的信息，在后续所有会话中都可以使用
```

## 4. L4 — 用户画像存储 (ProfileMemory)

### 4.1 设计目标

以 Key-Value 形式存储用户的结构化属性（姓名、职业、城市等），支持精确查询和增量更新。

**为什么用键值对保存用户画像数据？**

用户画像（Profile）保存的是"确定的事实"，而键值对（Key-Value）最适合存储这种结构化数据

**为什么不用自然语言保存？**

假设把用户画像也保存成长期记忆：

```
用户叫张伟。
用户是一名AI工程师。
用户在腾讯工作。
用户住在深圳。
```

现在用户问：

```
我叫什么？
```

如果用向量数据库，需要：

```
问题
    ↓
Embedding
    ↓
向量检索
    ↓
找到：
用户叫张伟
```

虽然能找到，但这是**语义检索**，存在几个问题：

- 检索速度比直接查键值慢。
- 相似度低时可能检索不到。
- 可能召回多条相似内容，需要再让模型判断。

而 Redis：

```
profile["name"]
```

直接得到：

```
张伟
```

时间复杂度基本就是 O(1)。

## 6. Prompt 构建器 (PromptBuilder)

### 6.1 职责

从四层记忆中检索数据，按固定顺序组装为 System Prompt，不包含 LLM 调用。

### 6.2 组装顺序

```
最终 System Prompt
│
├── [1] 基础角色设定
│   "你是一个有记忆能力的AI助手..."
│
├── [2] 【历史摘要】        ←── L2 SummaryMemory.load()
│   summary_text
│
├── [3] 【长期记忆】        ←── L3 LongMemory.load(limit=5)
│   - 记忆条目1
│   - 记忆条目2
│   ...
│
├── [4] 【用户画像】        ←── L4 ProfileMemory.load()
│   - name: 张伟
│   - job: Python后端开发工程师
│   ...
│
└── [5] 【最近聊天记录】    ←── L1 WindowMemory.load()
    user: ...
    assistant: ...
    user: {当前问题}
```

### 6.3 核心逻辑

```python
class PromptBuilder:
    def __init__(self, window, summary, long_memory, profile, user_id, session_id):
        self.window = window
        self.summary = summary
        self.long_memory = long_memory
        self.profile = profile
        self.user_id = user_id
        self.session_id = session_id

    def build(self, question):
        prompt = "你是一个有记忆能力的AI助手。请根据以下记忆信息来回答用户的问题。\n\n"

        # [2] L2 摘要
        summary_text = self.summary.load(self.session_id)
        if summary_text:
            prompt += f"【历史摘要】\n{summary_text}\n\n"

        # [3] L3 长期记忆 Top 5
        long_memories = self.long_memory.load(self.user_id, limit=5)
        if long_memories:
            prompt += "【长期记忆】\n"
            for memory in long_memories:
                prompt += f"- {memory}\n"
            prompt += "\n"

        # [4] L4 用户画像
        user_profile = self.profile.load(self.user_id)
        if user_profile:
            prompt += "【用户画像】\n"
            for key, value in user_profile.items():
                prompt += f"- {key}: {value}\n"
            prompt += "\n"

        # [5] L1 窗口 + 当前问题
        prompt += "【最近聊天记录】\n"
        for message in self.window.load():
            prompt += f"{message['role']}: {message['content']}\n"
        prompt += f"user: {question}"
        return prompt
```

### 模型选择

绝大多数企业都会优先使用小模型来做用户记忆提取

**为什么优先用小模型？**

用户记忆智能体的任务通常是：

- 提取用户画像（Profile）
- 判断是否需要保存长期记忆
- 更新摘要（Summary）

这些任务属于：

> **信息抽取（Information Extraction）**，而不是复杂推理

例如：用户说：

```
我叫张伟，目前是一名AI工程师，最近开始学习LangGraph。
```

Memory Agent 的工作只是输出：

```
{
  "profile": {
    "name": "张伟",
    "job": "AI工程师"
  },
  "long_memory": [
    "用户最近开始学习LangGraph。"
  ]
}
```

这类任务规则明确，不需要很强的推理能力，因此小模型完全可以胜任

**哪些记忆适合小模型？**

- ProfileAgent（推荐小模型）
- LongMemoryAgent（推荐小模型）
- SummaryAgent（视情况而定）

如果摘要只是：

```
最近10轮聊天
```

7B 小模型通常没问题。

如果：

```
500轮聊天
```

需要：

- 去重
- 合并
- 理解任务变化

这时大模型效果往往更好。

### 企业常见模型分工

| 智能体             | 推荐模型           | 原因                 |
| --------------- | -------------- | ------------------ |
| Main Agent      | 大模型（如 Qwen3系列） | 负责推理、规划、工具调用       |
| ProfileAgent    | 小模型（1.5B～7B）   | 信息抽取               |
| LongMemoryAgent | 小模型（1.5B～7B）   | 分类、提取长期事实          |
| SummaryAgent    | 小模型或中模型        | 简单摘要用小模型，复杂摘要用更强模型 |
| IntentAgent     | 小模型            | 意图识别               |
| RouterAgent     | 小模型            | 路由分类               |

## 1. MemoryManager — 更新调度器

### 1.1 职责

统一调度三个 Agent 的更新逻辑，在每轮对话结束后触发。

### 1.2 核心逻辑

```python
class MemoryManager:
    def __init__(self, conversation):
        self.profile_agent = ProfileAgent(conversation.profile)
        self.long_memory_agent = LongMemoryAgent(conversation.long_memory)
        self.summary_agent = SummaryAgent(conversation.summary)
        self.window = conversation.window
        self.user_id = conversation.user_id
        self.session_id = conversation.session_id

    def update(self, query):
        # 每轮必执行
        self.profile_agent.update(self.user_id, query)        # L4
        self.long_memory_agent.update(self.user_id, query)     # L3
        # 条件触发
        if len(self.window.load()) >= 10:                      # L2
            self.summary_agent.update(
                self.session_id, self.window.load()
            )
```

### 1.3 调度策略

| Agent                | 触发条件        | 执行频率  |
| -------------------- | ----------- | ----- |
| ProfileAgent (L4)    | 每轮对话后       | 每轮必执行 |
| LongMemoryAgent (L3) | 每轮对话后       | 每轮必执行 |
| SummaryAgent (L2)    | 窗口消息 ≥ 10 条 | 条件触发  |

## 2. L2 — 摘要提取 (SummaryAgent)

### 2.1 设计目标

模拟人类的**情景记忆**，将积累的历史对话压缩为精炼摘要，保留重要信息、去除闲聊冗余。

### 2.2 提取策略：增量摘要

采用"旧摘要 + 新对话 → 新摘要"的增量模式，避免全量重复处理。

```python
        self.prompt = self.get_prompt()
        self.agent = self.get_agent()
    def get_agent(self):
        return create_agent(model=self.model,system_prompt=self.prompt)
    def  get_prompt(self):
        prompt = """
          一: 你是一个对话摘要助手
              你的任务：根据【历史摘要】和【最近聊天记录】生成新的摘要。
              要求：
              1、保留重要信息
              2、去掉闲聊内容
              3、避免重复
              4、控制在200字以内
              5、使用第三人称描述
              6、只返回新的摘要 
        """
        return prompt

    def update(self,session_id, messages):
        # 读取旧摘要
        old_summary = self.summary_memory.load(session_id)
        # 最近聊天
        conversation = ""
        for message in messages:
            conversation += (
                f"{message['role']}："
                f"{message['content']}\n"
            )
        question=f"历史摘要：{old_summary}\n最近聊天记录：{conversation}\n请生成新的摘要："
        result = self.agent.invoke({"messages": [{"role": "user","content": question}]})
        summary = result["messages"][-1].content.strip()
        self.summary_memory.save(session_id=session_id,summary=summary)

        return summary
```

```python
    def update(self,user_id,user_input):
        result = self.agent.invoke({"messages": [{"role": "user","content": user_input}]})
        memory = result["messages"][-1].content.strip()

        if memory != "NONE":
            self.long_memory.save(user_id,memory)
```

```python
class ProfileAgent:
     def __init__(self, profile_memory):

    def update(self, user_id, user_input):
        result = self.agent.invoke(
            {"messages": [{"role": "user", "content": user_input}]}
```

### 4.4 与长期记忆的区别

| 维度   | L3 长期记忆            | L4 用户画像            |
| ---- | ------------------ | ------------------ |
| 输出格式 | 一句话自由文本            | 结构化 JSON           |
| 存储方式 | Redis ZSet (按分数排序) | Redis Hash (按字段索引) |
| 信息类型 | 偏好、计划、行为特征         | 姓名、职业、城市等稳定属性      |
| 更新方式 | 追加新记忆              | 按字段覆盖更新            |
| 价值评估 | LLM 评分 1~10        | 无评分                |

**各 Agent 的 LLM 调用开销**

| Agent           | LLM 调用次数/轮 | 调用目的        |
| --------------- | ---------- | ----------- |
| ProfileAgent    | 1          | 提取结构化用户属性   |

| SummaryAgent    | 0~1 (条件触发) | 生成增量对话摘要    |
| **合计**          | **2~3 次**  |             |
